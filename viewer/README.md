# 训练画面观看服务

在浏览器里看训练直播。训练用 `train.py --stream` 把画面推给 LiveKit,这个服务让人打开网址就能看到,
不用装客户端、不用填服务器地址、不用拿密钥。

---

## 一、当前状态

代码已完成(分支 `feat/stream-viewer`,目录 `viewer/`),连线上 LiveKit 验证过:
房间列表、发票、登录、页面出画面均正常。尚未部署到集群,目前在个人电脑上跑起来使用。

### 能做什么

- **自动列出正在推流的训练**:房间名、有没有画面、已经跑了多久,每 5 秒刷新一次
- **点一下就能看画面**
- **登录保护**:HTTP Basic Auth;没配凭据会拒绝启动,不会静默起一个开放页面
- **断线自动重连**,重连时自动换新票,看多久都不会因为票过期而断
- **观看者不接触密钥**:页面拿到的只是一张一小时过期的只读门票

其中断线重连只做了代码层面的检查,没有在浏览器里真实制造过断线,还没有实测过。

### 怎么用

前提:有训练正在推流,也就是启动命令里带了 `--stream`。

```bash
cd viewer
```

```bash
LIVEKIT_URL=ws://<LiveKit公网IP>:7880 LIVEKIT_KEYS="<key>: <secret>" VIEWER_AUTH_DISABLED=1 PORT=8899 python3 server.py
```

本机自己看时不需要登录,所以显式关掉。**不写这个变量会拒绝启动**,原因见下面的访问控制一节。

浏览器打开 `http://localhost:8899`,列表里点一个房间就能看。

`LIVEKIT_KEYS` 与 LiveKit 服务端的凭据一致,形如 `devkey: 一串随机字符`,可以从集群 Secret 里读:

```bash
kubectl get secret <release>-livekit-auth -o jsonpath='{.data.keys}' | base64 -d
```

## 二、实现

### 组成

```
viewer/
├── server.py                        后端:四个接口,只用 Python 标准库
├── static/index.html                页面
├── static/livekit-client.umd.min.js LiveKit 官方浏览器 SDK,本地引用不走 CDN
└── Dockerfile                       python:3.11-slim,不装任何依赖
```

### 为什么需要后端,不能是纯网页

网页源码会完整发到用户电脑上,谁都能看。而连 LiveKit 必须持有"门票",门票又必须用 API 密钥签发 ——
密钥写进页面等于公开。所以密钥留在后端,后端签好票再给页面。

房间列表同理:查询它需要管理员权限的票,而且 LiveKit 的接口不允许网页跨站调用,只能由后端代查。

```
浏览器 ──① 要房间列表、要票──► 观看服务(持有密钥)──► LiveKit
      ──② 拿着票直接收流──────────────────────────► LiveKit
```

### 后端接口

| 接口 | 作用 |
|---|---|
| `GET /` | 观看页面 |
| `GET /api/rooms` | 正在推流的房间列表 |
| `GET /api/token?room=X` | 发一张观众票 |
| `GET /healthz` | 存活和配置状态 |

票里写死了权限,页面无法影响:只能进指定的那一个房间、只能看、不能推流、一小时后过期。
另外只对**已存在的房间**发票 —— 否则任何打开页面的人都能让 LiveKit 凭空建出空房间。

### 访问控制

**HTTP Basic Auth**。浏览器原生支持,不需要登录页 —— 第一次访问收到认证挑战,浏览器自动弹出
输入框,之后每个请求自动带上凭据。

约定的环境变量是 `VIEWER_AUTH_USERNAME` / `VIEWER_AUTH_PASSWORD`,由部署侧从 Secret 注入(见问题 1)。

**没配凭据会拒绝启动**,除非显式设置 `VIEWER_AUTH_DISABLED=1`。这样"忘了配"是一眼可见的启动失败,
"故意不配"则是写下来的决定 —— 因为这个页面会列出所有正在跑的训练并直接播放,两者要是产生同样的结果,
从外面根本看不出区别。

保护范围是**页面和全部接口**,只放行 `/healthz`(k8s 探针不带凭据,挡了会让 pod 反复重启,
而且症状像应用崩溃,很难联想到鉴权)。只挡页面是不够的,不然直接调 `/api/token` 就绕过去了。

密码比较用常数时间比较,不会因为响应时间差被逐字符试出来。

### 页面

深色界面,两屏:房间列表 → 点进去看画面。视频用 LiveKit 官方 SDK 播放。

**断线自动重连**:连接断开后自动重连,每次重连都向后端重新取一张票,间隔从 2 秒退避到 30 秒,
状态显示在画面上方。因为票只在加入房间时校验,所以"重连时用新票"这一条同时解决了票过期的问题 ——
看多久都不会因为票过期而断。用户主动点返回则不再重连。

**连上 15 秒还没有画面时,会提示可能是网络挡住了 UDP 媒体端口**。因为信令走 TCP、画面走 UDP,
防火墙只放行 TCP 时的表现是"连接一切正常但永远黑屏",不提示的话用户只能看到一片黑,无从判断。

### 配置项

| 环境变量 | 说明 |
|---|---|
| `LIVEKIT_URL` | **后端**访问 LiveKit 的地址。部署在集群里时填集群内 Service 地址 |
| `LIVEKIT_PUBLIC_URL` | **页面**访问 LiveKit 的地址,填公网 IP 或域名。不填则与上一项相同 |
| `LIVEKIT_KEYS` | LiveKit 原生凭据格式 `key: secret`,直接挂服务端那份 Secret |
| `LIVEKIT_API_KEY` / `LIVEKIT_API_SECRET` | 拆开写的形式,设置了则优先 |
| `PORT` | 监听端口,默认 8080 |
| `TOKEN_TTL` | 票的有效期(秒),默认 3600 |
| `VIEWER_AUTH_USERNAME` / `VIEWER_AUTH_PASSWORD` | 登录用户名和密码。不设则拒绝启动 |
| `VIEWER_AUTH_DISABLED` | 设为 `1` 表示确实要在无鉴权下运行 |

两个地址必须分开填。混用的后果:页面拿到集群内网地址连不上,或者后端绕公网兜一圈,白付流量费。

凭据直接复用 LiveKit 服务端那份 Secret,不要另存一份。两份副本迟早会不一致,而不一致的表现是
"认证过了但随即失败",看起来完全不像配置问题,很难查。

## 三、现有问题

代码侧目前没有已知缺口,三条都在部署侧,其中 Helm 模板已经完成。

### 1. 还没有镜像,因此还没跑起来

Helm 模板已完成(PR #22,`docker/charts/templates/viewer.yaml`),缺的是镜像。

**要做的**:CI 增加一条独立的镜像构建。不要和训练镜像绑在一起 —— 训练镜像 25 GB,这个只有几十兆,
改一行页面文字不该重打训练镜像,两者发布节奏也应该分开。

容器需要两份凭据,约定如下:

| 来源 | 注入成 | 作用 |
|---|---|---|
| LiveKit 的 Secret(复用服务端那份,不要另建) | `LIVEKIT_KEYS` | 签票、查房间 |
| `physical-ai-auth` | `VIEWER_AUTH_USERNAME` / `VIEWER_AUTH_PASSWORD` | 页面登录 |

```bash
kubectl create secret generic physical-ai-auth --from-literal=username=<用户名> --from-literal=password='<密码>'
```

登录凭据缺失时服务拒绝启动,所以这份 Secret 不能是可选的 —— Helm 侧已做成硬约束,没提供就渲染失败。

### 2. 页面用 https 打开时连不上(卡在上游)

LiveKit 现在是明文的 `ws://`。页面用 http 打开正常,一旦用 https 打开,浏览器会拦截明文连接
(加密页面里不允许有明文通道)。

同一件事还关系到登录的有效性:**Basic Auth 只在 https 下才是真正的保护**,明文 http 时凭据以
base64 传输,而 base64 不是加密,链路上可以还原。在证书就绪前,登录挡的是"误入",不是"攻击"。

**当前状态**:上游的 livekit chart 没有任何 TLS 配置入口,`wss://` 落不了地,因此这条暂时挂起。

**将来要做的**:给 LiveKit 配域名和证书,信令改成 `wss://`。观看服务本身不用改代码,
把 `LIVEKIT_PUBLIC_URL` 配成 `wss://` 即可。推荐用一个域名加 Ingress 统一终止 TLS,
页面和信令走同一个域名,只需要一张证书;画面走 UDP 直连,不经过 Ingress,不受影响。

### 3. 同一个 pod 里的多个训练仍会挤进同一个房间

Helm 侧已经不再写死 `LIVEKIT_ROOM`,改为注入 `JOB_NAME`(pod 名),所以不同 pod 之间已经分开了。
但 StatefulSet 是单副本,pod 名基本等同 release 名,**在同一个 pod 里手工起的两个训练仍然同名**。

**要做的**:房间名要带上只有那次运行才知道的信息(任务名、启动时刻),这部分在
`livekit_stream.py` 里,Helm 侧只能做到"不写死"。带上任务名还有个附带好处:
观看列表能直接显示在训练什么,而不是一串 pod 名。
